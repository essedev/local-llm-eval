# MTP speculative decoding su Qwen3.8-27B, M5 base 32 GB

Misure del 2026-08-17. Domanda: quanto guadagna il decode attivando la testa MTP nativa del modello, e cosa serve per attivarla davvero.

## Risultato

| Configurazione | Decode tok/s (3 run) | min-max |
|---|---|---|
| mlx-lm 0.31.3 ufficiale, checkpoint lmstudio-community, default | 8,03 | 7,96-8,11 |
| fork `feat/mtp-native`, checkpoint fuso, senza `--mtp` | 7,58 | 7,48-7,71 |
| fork `feat/mtp-native`, checkpoint fuso, con `--mtp` | 11,75 | 11,66-11,83 |

Speedup MTP a parità di runtime: **1,55x**. Rispetto al default che si ottiene installando normalmente: **1,46x**.

Peak memory identico in tutte le configurazioni (15,8 GB): il drafter aggiunge 270 MB, ininfluenti.

La baseline del fork è il 6% sotto quella della release ufficiale. Non abbiamo indagato: per il confronto MTP conta il rapporto a parità di runtime, e il numero da citare all'esterno resta quello del setup ufficiale.

## Cosa serve per attivare MTP (2026-08-17)

Non è un flag. Quattro passaggi, nessuno documentato in un posto solo:

1. **Il supporto non è nel pacchetto ufficiale.** mlx-lm 0.31.3 è l'ultima release e non ha MTP: serve il branch `feat/mtp-native` del fork AirRunner ([PR #990](https://github.com/ml-explore/mlx-lm/pull/990), ancora aperta).
2. **Nessun checkpoint MLX pubblico di Qwen3.8-27B conserva la testa MTP.** Verificato su `lmstudio-community/Qwen3.8-27B-MLX-4bit` e `mlx-community/Qwen3.8-27B-4bit`: zero chiavi MTP su 2180. Il config però dichiara `mtp_num_hidden_layers: 1`, quindi il fork rifiuta di caricare (la release ufficiale non se ne accorge perché ignora la chiave).
3. **I pesi del drafter sono distribuiti a parte**: [mlx-community/Qwen3.8-27B-MTP-4bit](https://huggingface.co/mlx-community/Qwen3.8-27B-MTP-4bit), 270 MB, 31 tensori. Non è un modello autonomo: contiene solo la testa, il target fornisce embedding e lm_head a runtime.
4. **Le chiavi vanno rinominate e fuse nel target.** Il drafter le espone come `fc.*`, `layers.0.*`, `norm.weight`; `TextModel` le cerca sotto `language_model.mtp.*`. Lo script `scripts/fuse-mtp-weights.py` crea una directory con symlink ai pesi originali (nessuna copia dei 15 GB) più un file con i 31 tensori rinominati e un index aggiornato.

## Riproduzione

```bash
# 1. ambiente isolato col fork
uv venv mtp-env --python 3.12
uv pip install --python mtp-env/bin/python "mlx-lm @ git+https://github.com/AirRunner/mlx-lm.git@feat/mtp-native"

# 2. drafter da HuggingFace (270 MB)
mtp-env/bin/python -c "from huggingface_hub import snapshot_download; print(snapshot_download('mlx-community/Qwen3.8-27B-MTP-4bit'))"

# 3. fusione dei pesi nel target (symlink, non copia)
mtp-env/bin/python scripts/fuse-mtp-weights.py /percorso/output

# 4. confronto con e senza MTP
scripts/bench-mtp.sh
```

Dati grezzi in `mtp-2026-08-17.csv`. Baseline dei tre modelli senza MTP in `THROUGHPUT-2026-08-17-1256.md`.

## Perimetro

Un solo prompt, un solo task (generazione di codice Python, 400 token), una sola macchina, 4-bit. Lo speedup MTP dipende da quanto il draft indovina, quindi varia col tipo di testo: su testo molto prevedibile sale, su testo con molta entropia scende. Non abbiamo misurato la qualità dell'output con e senza MTP, che per costruzione dovrebbe essere identica (il target verifica ogni token proposto) ma non è stato verificato qui.
